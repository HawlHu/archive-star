EXES V5.9.1 LTS 跨平台相容加密協議實作與驗證：ChaCha20、HKDF-SHA-512、HMAC-SHA-512 與 Base62 結構化編碼

<<Implementation and Evaluation of EXES V5.9.1 LTS: Cross-Platform ChaCha20 Encryption with HKDF-SHA-512, HMAC-SHA-512, and Base62 Structural Encoding>>

摘要 (Abstract)

隨著資訊系統迭代，維持 Visual Basic 6、早期 PHP 等遺留環境與現代 Web 前端之間的可重現、可驗證加密互通，仍是企業系統維護上的實務難題。本研究針對 「EXES (EXtended Encryption Standard) V5.9.1 LTS」 自訂加密協議進行架構與實作層分析。V5.9.1 LTS 已不再沿用 V5.8 的 Dual-Sponge 與 264-bit 自訂 MAC 架構，而改採標準 ChaCha20 20-round block function、 HKDF-SHA-512 進行加密金鑰與驗證金鑰分離、SHA-512 進行 nonce derivation，並以 HMAC-SHA-512 對版本、Salt、IV、加密長度欄位與密文執行 Encrypt-then-MAC 式完整性驗證。Base62 拓撲乘數則保留為 X5A wire format 的結構化編碼與 canonical validation，不再被視為密碼學完整性的主要來源。

在本次展示環境中，功能性與邊界測試最高執行 500,000 次；統計分析串流為 3,216,000 bits，觀測到位元組 Shannon entropy 7.9995 bits/byte， Monobit、Block Frequency、Cumulative Sums、Longest Run 與 byte Chi-square 等檢定的 p-value 均高於本次設定的 α=0.01，且測試樣本中的 Body/Header 竄改未出現被接受案例。 這些結果屬於實作層測試觀測，不能取代形式化安全證明、第三方密碼分析或標準化安全認證。

術語說明：EXES 名稱中的 “Encryption Standard” 為專案命名；EXES 本身是自訂協議／wire format，並非 NIST、IETF 或 ISO 已標準化的 cipher suite。

 

關鍵字 (Keywords)

EXES V5.9.1 LTS、ChaCha20、HKDF-SHA-512、HMAC-SHA-512、Encrypt-then-MAC、Base62、跨語言互通、Legacy Systems、NIST SP 800-22 Rev. 1a

 

英文摘要 (English Abstract)

Maintaining reproducible and verifiable encrypted interoperability between legacy environments such as Visual Basic 6 / early PHP and modern Web front-ends remains a practical enterprise maintenance challenge. This study analyzes the custom EXES V5.9.1 LTS protocol and its cross-language implementation. Unlike the earlier V5.8 Dual-Sponge/264-bit custom-MAC design, V5.9.1 LTS uses the RFC 8439 ChaCha20 20-round block function, HKDF-SHA-512 for separation of encryption and authentication keys, SHA-512-based nonce derivation, and HMAC-SHA-512 in an Encrypt-then-MAC-style composition over protocol metadata and ciphertext. Its Base62 topology transform is retained as a structural/canonical wire encoding layer rather than as the cryptographic integrity mechanism.

In the demonstration run, functional/boundary testing was configured up to 500,000 iterations and the statistical stream contained 3,216,000 bits. Observed byte entropy was 7.9995 bits/byte; the implemented Monobit, Block Frequency, Cumulative Sums, Longest Run, and byte Chi-square tests produced p-values above α=0.01, while no accepted Body/Header tampering was observed in the tested samples. These measurements provide implementation-level evidence only and do not constitute a formal cryptographic proof, third-party cryptanalysis, or standards certification.

 

一、 背景 (Background)

在金融、製造、內部資訊系統與長生命週期設備中，遺留系統（Legacy Systems）仍相當常見，例如 Visual Basic 6、32-bit Windows 與早期 PHP 執行環境。 這類平台常無法直接採用現代函式庫介面，或在 unsigned 32-bit arithmetic、UTF-8、CSPRNG 與 API 相容性上產生差異。 EXES V5.9.1 LTS 的研究重點因此不是重新發明單一密碼原語，而是將 ChaCha20、HKDF、SHA-512、HMAC 等既有原語，以固定的 X5A wire format 實作到不同語言與不同年代的 runtime 中。

其中，瀏覽器版本的安全亂數採 Web Cryptography API 的 crypto.getRandomValues()（IE11 LTS 路徑使用 msCrypto.getRandomValues()）； 舊版 VB6 則以 Windows CryptoAPI 的 CryptGenRandom 取得 Salt/IV。若可信 CSPRNG 不可用，V5.9.1 LTS 採 fail-closed，不退回 Math.random()、Rnd() 或一般 PRNG。

 

二、 動機 (Motivation)

本研究的動機在於降低「同一協議在不同語言中產生不同位元結果」的互通風險，並改善 V5.8 稽核時發現的設計問題。 V5.9.1 LTS 改用標準 ChaCha20 block function（包含 feed-forward），避免直接輸出自訂 permutation 的 raw state； 同時以 HKDF-SHA-512 的不同 info label 分離 encryption key 與 MAC key，再以 HMAC-SHA-512 驗證密文與解密所需 metadata。

因此，本版較精確的描述是「自訂 wire protocol + 標準密碼原語 + Encrypt-then-MAC 式認證加密組合」。 本文不將其宣稱為 RFC 8439 所定義的 ChaCha20-Poly1305 AEAD，也不把測試工具的通過結果等同於第三方安全認證。

 

三、 目的 (Purpose)

本研究的主要目的包含：

  • 分析 EXES V5.9.1 LTS 中 ChaCha20 的標準 20-round block function、counter 使用方式與 96-bit nonce 輸入。
  • 驗證 HKDF-SHA-512 以 EXES-V5.9-ENC / EXES-V5.9-MAC label 進行 encryption/MAC key separation 的跨語言一致性。
  • 分析 HMAC-SHA-512 對版本、Salt、IV、加密長度欄位與 ciphertext 的完整性保護，以及 constant-time tag comparison。
  • 確認 Base62 Topology Multiplier 的角色為 wire encoding 與格式前置驗證，而非取代 MAC 的密碼學防篡改機制。
  • 以 deterministic test vector 驗證 JavaScript、Python、Go、Java、Android-Java、C++、PHP、Ruby、Swift 等版本的 bit-for-bit X5A interoperability。
  • 透過邊界、竄改、Unicode、錯誤金鑰、隨機性與效能測試評估實作品質，並清楚區分「測試結果」與「密碼學安全證明」。

 

四、 研究方法 (Methodology)

本研究採用靜態程式碼審查、deterministic cross-language vector 與動態壓力／統計測試三種方法交叉驗證。

4.1 V5.9.1 LTS 核心資料流程

UTF-8 key material + 144-bit Salt
        │
        └─ HKDF-SHA-512
             ├─ info "EXES-V5.9-ENC" ─► 256-bit ChaCha20 key
             └─ info "EXES-V5.9-MAC" ─► 512-bit HMAC-SHA-512 key

144-bit IV
        └─ SHA-512( IV || "EXES-V5.9-NONCE" )[0..11]
                                      └─► 96-bit ChaCha20 nonce

Plaintext ─► ChaCha20(counter=1) ─► padded ciphertext
                                      │
X5A + Salt + IV + encrypted length ───┼─► HMAC-SHA-512 ─► 512-bit tag
                                      │
                                      └─► Base62 topology wire encoding

此設計採「先加密、再對密文與必要 metadata 驗證」的 Encrypt-then-MAC 思路。完整 HMAC tag 為 64 bytes（512 bits）； 但 512-bit tag 不代表整體系統具有 512-bit security strength，整體強度仍受 ChaCha20 256-bit key 與實際輸入 key/password entropy 限制。

4.2 X5A wire format

X5A | Salt(30 chars) | IV(30 chars) | Encrypted Length(10 chars)
    | Ciphertext(5 chars / padded 3 bytes) | HMAC-SHA-512 Tag(110 chars)

每個 24-bit value 以五個 Base62 字元表示，使用 expanded = val * 54 + (val % 54) 的 canonical relation。 解碼時不符合關係者可在進入密碼驗證前被拒絕；真正的訊息完整性仍由 HMAC-SHA-512 提供。

4.3 跨平台與文字編碼

  • JavaScript：ES5-style LTS core，目標 IE11～現代 Chrome；CSPRNG 使用 Web Crypto / msCrypto。
  • VB6：XP～Windows 11 版以純 VB6 實作 SHA-512/HMAC/HKDF/strict UTF-8，亂數使用 CryptoAPI。
  • PHP：另提供 PHP 4.3.11～8.x source-compatible LTS 設計；新版 PHP 可使用原生 hash/hmac 加速，舊版則 pure-PHP fallback。
  • Unicode：跨語言以 UTF-8 / RFC 3629 為共同 byte representation；JavaScript 版本拒絕未配對 UTF-16 surrogate，避免舊版 replacement-character 等價 key 問題。

4.4 自動化測試方法

  • 功能／邊界：Round-trip、Body/Header tamper、wrong key、truncate/extend、Null byte、Unicode、Zalgo、large payload、type conversion 與重入／併發呼叫一致性。
  • 統計：Shannon entropy、Monobit、Block Frequency、Cumulative Sums、Longest Run 與 byte Chi-square；顯著水準 α=0.01。
  • 執行模型：瀏覽器 dashboard 以 requestAnimationFrame 分批排程與 Promise-based concurrency 保持 UI 回應；這並非 Web Worker 多執行緒測試。
  • 記憶體：統計計數器採固定 256-bin / bit counters，可近似 O(1) 額外統計記憶體；EXES 加解密本體仍需保存輸入、輸出與 ciphertext buffer，因此對訊息長度是 O(n)，不應稱為整體 O(1) encryption memory。

4.5 跨語言驗證狀態

在目前建立環境中，JavaScript/Node、Python、Go、Java、Android-Java profile、C++、PHP 8.4、Ruby、Swift 已實際執行固定 Salt/IV 的 X5A vector 並與 canonical JavaScript 密文逐字相同。 C#、VB.NET、PowerShell、VB6 與 ASM core 因本環境缺乏對應編譯器/runtime，屬 source-audited；其中 PHP 4.3.11 與 Windows XP/VB6 的舊平台支援也應視為 source-level compatibility target，不能冒充已在該舊 runtime 實機通過。

 

五、 研究結果 (Results)

以下數據取自文件內附的展示環境報告；數值會受瀏覽器、CPU、runtime、樣本數與 Salt/IV 隨機結果影響，因此應視為一次可重現流程的觀測結果：

  • 功能／邊界：Body tamper、Header tamper、truncate、Null byte 等展示測試未觀察到異常放行；wrong-key 與 tag mismatch 會 fail-closed。
  • 位元組熵：總體 Shannon entropy = 7.9995 bits/byte（理論上限 8.0）。高 entropy 僅表示樣本分佈接近均勻，不等於證明密碼學安全。
  • 雪崩觀測：Key SAC = 50.03%；PT SAC = 49.92%。
  • 實際 p-value：Monobit 0.068407；Byte Chi-square 0.541315 (df=255)；Block Frequency 0.577562；CumSums F/R 0.084537 / 0.087873；Longest Run 0.986104；本次 α=0.01。
  • 統計資料量：本次 statistical stream = 3,216,000 bits；功能性邊界迴圈另設定最高 500,000x，不能將「500,000x」誤寫成每一種統計檢定都使用 500,000 組樣本。
  • 效能：本次報告記錄 KDF/初始化約 0.60 ms，加密約 2271 KB/s、解密約 4711 KB/s；這些是特定展示環境的 benchmark，不是跨硬體保證值。

依 NIST SP 800-22 Rev. 1a 的說明，統計檢定可作為觀察隨機性的一個起點，但不能取代 cryptanalysis；因此本文不再使用「100% immunity」、「絕對安全」、「完美防禦」等超出測試證據的描述。

 

六、 研究發現 (Findings)

本研究依 V5.9.1 LTS 現行架構得到以下實作層發現：

  1. Base62 topology 是格式濾波，不是 MAC： val * 54 + (val % 54) 讓部分非法五字元組可提早被拒絕，適合作為 canonical/structural validation； 但攻擊者仍可能製造其他「合法編碼」值，因此 cryptographic integrity 必須依賴 HMAC-SHA-512。
  2. 金鑰分離已由 HKDF label 取代 V5.8 的 0x44/0x55 dual-sponge domain： encryption key 與 MAC key 分別以 EXES-V5.9-ENC、EXES-V5.9-MAC derivation context 產生，降低同一 raw key 直接跨用途使用的風險。
  3. HMAC 驗證先於明文釋出： 解密端先重新計算 HMAC-SHA-512，並以 constant-time 比較 tag；驗證通過後才進行 ChaCha20 解密，可降低 bit-flipping 後輸出未驗證明文的風險。
  4. V5.8 raw-state keystream 問題已移除： V5.9.1 使用 RFC 8439-style ChaCha20 block function 的 feed-forward output，不再直接把自訂 permutation 的內部 state words 序列化成 keystream。
  5. Unicode key 處理更明確： strict UTF-8 / strict UTF-16 surrogate handling 使非法 surrogate 不再靜默轉成相同 U+FFFD byte sequence；合法 Unicode 的 byte representation 依 RFC 3629 統一。
  6. 跨語言 bit-for-bit vector 是重要的 regression gate： 固定 plaintext/key/Salt/IV 時，各 full port 應產生完全一致的 X5A... 密文；這比僅測「自己加密、自己解密」更能抓出 endian、overflow、UTF-8 與 unsigned arithmetic 差異。

6.1 安全邊界與限制

  • 自訂協議：EXES 並非經 NIST/IETF 標準化的 AEAD；目前組合雖採標準原語與 Encrypt-then-MAC 思路，仍需要獨立密碼分析與長期公開檢視。
  • HMAC 512-bit ≠ 512-bit overall security：ChaCha20 encryption key 是 256-bit；若使用 41 位均勻隨機 Base62 key，其理論 entropy 約 244 bits，而人類可記憶密碼通常更低。
  • HKDF 不是 password-hardening KDF：若輸入是低 entropy 人類密碼，建議先採 Argon2id 等 memory-hard password KDF，再將高 entropy key material 提供給 EXES；HKDF 的主要用途是 extract/expand 與 key separation。
  • 統計測試不是安全證明：NIST 明確指出 statistical testing 不能取代 cryptanalysis。
  • 記憶體複雜度：目前 full-message implementation 的加解密 buffer 隨輸入長度成長；O(1) 僅適用於本測試工具的串流統計 counters，而不是 EXES 整體。

 

七、 未來可延伸研究 (Future Work)

未來可延伸方向包括：

  • 與標準 AEAD 的正式比較：以 RFC 8439 ChaCha20-Poly1305 作 baseline，比較 EXES Encrypt-then-MAC 在 wire overhead、legacy portability、failure behavior 與效能上的差異；亦可研究未來改採 XChaCha20-Poly1305 的可能性。
  • 低 entropy 密碼強化：加入可選的 Argon2id / 其他 password-hardening 前級，並明確區分 machine-generated key 與 human password 的 threat model。
  • 後量子 key establishment：研究以 ML-KEM / FIPS 203 建立共享 secret，再將共享 secret 輸入 EXES 對稱加密層，而不是將 KEM「塞進」ChaCha 初始化內部。
  • WebAssembly 效能最佳化：保留 X5A wire compatibility，將現代瀏覽器的 SHA-512/ChaCha20 熱點改為 WASM，同時維持 IE11 的 ES5 fallback。
  • 形式化與第三方分析：增加 parser fuzzing、differential testing、timing analysis、nonce/key misuse 測試，以及邀請外部研究者進行 cryptanalysis；必要時考慮以成熟 AEAD library 取代自訂 composition。

九、 相關附件：實機環境操作與稽核步驟

欲在本地端重現本頁展示的稽核流程，可依下列步驟：

  1. 步驟一：建置測試環境
    使用本頁下載套件中的 audit/utility_exes_v591_real_statistics.html，或線上 Crypto Console。 稽核頁本身使用 async/await 與現代瀏覽器 API，因此建議 Chrome / Edge / Firefox；「EXES 核心支援 IE11」與「audit dashboard 可在 IE11 執行」是兩個不同相容性範圍。
  2. 步驟二：確認核心版本
    EXES cipher 應以 X5A 開頭，並確認核心為 V5.9.1 LTS。可先執行 exesSelfTest() / environment self-test，再進行壓測。
  3. 步驟三：執行功能與邊界測試
    執行 Round-trip、wrong key、Body/Header tamper、truncate/extend、Null byte、Unicode、Zalgo、large payload 等項目。 Dashboard 的 Promise-based concurrent calls 用於檢查重入與共享狀態問題；JavaScript 同步密碼核心本身不是多執行緒。
  4. 步驟四：執行真實統計計算
    執行 Shannon entropy、NIST Monobit、Block Frequency、Cumulative Sums、Longest Run 與 byte Chi-square。 本頁採 α=0.01；單一 p-value 低於門檻是統計警示，應以多批樣本與 pass proportion 分析，不宜直接宣稱存在或不存在密碼學漏洞。
  5. 步驟五：解讀報告
    報告中的 PASS / SECURE 字樣只代表本工具的測試規則結果，不是 NIST/FIPS/ISO 認證。研討會呈現時建議同時揭露樣本數、runtime、硬體、瀏覽器版本與測試工具版本。
